О документе: ниже — формулировка проблемы и «канонический» алгоритм для RAG-системы (retrieval-augmented generation), которая должна уметь находить группы и студентов для конкретного предмета в базе NewStud, несмотря на расхождения между учебным планом и заведёнными группами.

Проблема (Problem Statement)

Даны: факультет (NFirm), учебный план (Educ_Plan.PrK_Plan), учебный год начала (Year_Study), курс (Course), семестр (Semester=1|2), предмет (Subject_Name.PrK_Subject_Name).

Нужно: определить «целевую аудиторию» предмета в текущем семестре — то есть:

  • список подпланов (Sub_Plan), к которым предмет относится в этом семестре по учебному плану;
  • группы (Group_Stud) набора (Plan_Year_Enter) на этот год/курс;
  • студентов (Entrant) из этих групп, с учётом последнего «живого» статуса (Status.FK_Status_Type ∈ {1,2,3,4,5,9}).

Ключевая сложность: в реальных данных группы набора часто не привязаны к подпланам (Group_Stud.FK_Sub_Plan IS NULL), тогда как предмет в Comp_Term привязан к конкретному подплану. Это создаёт «разрыв» между планом и фактическими группами.

Мини-словарь

  • NFirm — факультет.
  • Plan — Educ_Plan.
  • SubPlan — Sub_Plan (подплан/поток внутри плана).
  • Plan_Year_Enter — запуск плана для конкретного года набора (Year_Enter).
  • Comp_Term — компоненты плана по семестрам (Num_Term), несут нагрузки и ссылку на подплан (FK_Sub_Plan).
  • Group_Stud — группы студентов в рамках конкретного запуска плана; могут иметь FK_Sub_Plan или быть общими (NULL).
  • Entrant — студент, привязанный к группе (FK_Group_Stud, Owner_Group).
  • Status — история статусов; нужен последний статус из набора «живых».

Данные и соответствия

  • Семестр в терминах Comp_Term: Num_Term = (Course - 1) * 2 + Semester (1..12).
  • Год набора, соответствующий заданным Year_Study, Course: Year_Enter = Year_Study - (Course - 1).
  • Связь плана и запуска: Plan_Year_Enter (NFirm, FK_Plan, Year_Enter).

Канонический алгоритм (для retrieval-шага RAG)

  • Определить Num_Term и Year_Enter по входным Year_Study, Course, Semester.
  • Убедиться, что план запущен: найти Plan_Year_Enter по NFirm = :nfirm AND FK_Plan = :planId AND Year_Enter = :yearEnter. Если записи нет — данных для этого набора/курса/семестра не существует.
  • Найти подпланы предмета в этом семестре по плану: из Subject_Name_Order (sno) и Comp_Term (ct) с фильтрами ct.Num_Term = :numTerm и валидностью ct.Beg_Act/ct.End_Act, получить множество FK_Sub_Plan.
  • Найти группы запуска плана: сначала точные (FK_Sub_Plan IN (:subplans)), затем fallback на общие (FK_Sub_Plan IS NULL), если точных нет или подпланов нет.
  • Отфильтровать «живых» студентов: взять последний статус по каждому Entrant и оставить только FK_Status_Type IN (1,2,3,4,5,9).
  • Вернуть: Sub_Plan (если есть), Group_Stud, список Entrant (ФИО из Person), опционально флаг источника (точный подплан или общий) для объяснимости.

Зачем fallback: он закрывает реальный кейс, когда предмет в Comp_Term уже «раскидан» по подпланам, а группы набора ещё не размечены по подпланам и заведены как общие.

Псевдо-SQL (шаблоны для поиска)

Подпланы предмета

-- inputs: @Nfirm, @PlanID, @SubjectID, @Num_Term, @Year_Enter
SELECT DISTINCT ct.FK_Sub_Plan
FROM Subject_Name_Order sno
JOIN Comp_Term ct
  ON ct.NFirm      = sno.NFirm
 AND ct.CodOrderID = sno.PrK_Subject_Order
WHERE sno.NFirm = @Nfirm
  AND sno.FK_Plan = @PlanID
  AND sno.FK_Subject_Name = @SubjectID
  AND ct.Num_Term = @Num_Term
  AND ct.Beg_Act <= @Year_Enter
  AND (ct.End_Act = 0 OR ct.End_Act >= @Year_Enter);

Группы запуска (точные → потом общий fallback)

-- exact
SELECT gs.*
FROM Group_Stud gs
WHERE gs.NFirm=@Nfirm
  AND gs.FK_Plan_Year=@PYE
  AND gs.FK_Sub_Plan IN (SELECT FK_Sub_Plan FROM #Subplans WHERE FK_Sub_Plan IS NOT NULL);

-- fallback
SELECT gs.*
FROM Group_Stud gs
WHERE gs.NFirm=@Nfirm
  AND gs.FK_Plan_Year=@PYE
  AND gs.FK_Sub_Plan IS NULL;

Последний «живой» статус

;WITH LastStatus AS (
  SELECT s.FK_Entrant, s.FK_Status_Type,
     ROW_NUMBER() OVER (
       PARTITION BY s.FK_Entrant
       ORDER BY s.Status_Date DESC, s.PrK_Status DESC
     ) rn
  FROM Status s
  WHERE s.NFirm=@Nfirm
)
SELECT *
FROM LastStatus
WHERE rn=1 AND FK_Status_Type IN (1,2,3,4,5,9);

Типовые граничные случаи

  • Нет Plan_Year_Enter для (NFirm, PlanID, Year_Enter): план не запускался в этот набор. Возвращать пустой результат с пояснением.
  • Comp_Term указывает подплан, а групп с таким подпланом нет (самая частая ситуация на 1-м курсе): fallback на общие группы запуска (FK_Sub_Plan IS NULL).
  • Comp_Term без подплана (FK_Sub_Plan IS NULL): искать только общие группы запуска.
  • Статусы студентов не «живые» или отсутствуют: такие записи исключаются из аудитории.

Анти-паттерны (чего избегать)

  • Фильтровать Group_Stud только по подпланам без fallback — приведёт к пустым спискам, хотя заниматься нужно.
  • Игнорировать валидность компонента по году набора (ct.Beg_Act/End_Act) и попадание семестра (Num_Term).
  • Не проверять «живость» последнего статуса — приведёт к включению отчисленных/окончивших.

Что можно индексировать/кэшировать (для RAG подсказок)

  • Фильтры часто идут по (NFirm, FK_Plan, Year_Enter) и (NFirm, FK_Plan_Year); полезны составные индексы в Plan_Year_Enter, Group_Stud.
  • Для статусов — индекс по (NFirm, FK_Entrant, Status_Date DESC) ускорит выбор последнего статуса.
  • Для «учебной логики» — индекс по Comp_Term (NFirm, CodOrderID, Num_Term, Beg_Act, End_Act).

Краткий ответ модели (пример)

«Для предмета 155 по плану 671 на 1 курсе, семестр 1 (2025/26) Comp_Term указывает подплан 2470, но группы набора-2025 заведены как общие (FK_Sub_Plan IS NULL). Поэтому аудиторию формируем из групп Plan_Year_Enter=6855 с FK_Sub_Plan IS NULL, отфильтровав студентов по последнему «живому» статусу.»

Что это даёт RAG-агенту

  • Корректно объясняет «почему пусто» и что делать (fallback).
  • Возвращает осмысленные списки даже при неполной разметке подпланов.
  • Устойчив к ключевым аномалиям данных, типичным на первых курсах.
