Контекст проблемы

При работе с процедурами получения учебных планов (например, am_GetEducPlans) может возникать ситуация, когда один и тот же учебный план (Educ_Plan) возвращается несколько раз с разным количеством студентов.

На первый взгляд это выглядит как ошибка в SQL-запросе, однако на практике корень проблемы почти всегда лежит в данных таблицы Plan_Year_Enter.

Назначение Plan_Year_Enter

Plan_Year_Enter фиксирует факт запуска учебного плана для конкретного года набора и инспектора.
Одна запись — это не «план», а административное оформление набора.

Ключевые поля

  • FK_Plan — учебный план
  • Year_Enter — год набора
  • NFirm — факультет
  • FK_Insp — инспектор
  • PrK_Plan_Year — идентификатор запуска плана

Ключевая особенность

В базе нет ограничения уникальности на комбинацию (FK_Plan, Year_Enter, NFirm).
Это позволяет существовать нескольким строкам Plan_Year_Enter для одного и того же плана и года.

Реальная причина дублей

Дубли появляются из-за административных факторов:

  • повторное заведение набора,
  • параллельная работа инспекторов,
  • корректировки задним числом,
  • историческое наследие данных.

Это системная особенность модели, а не ошибка пользователя.

Как это влияет на запросы

Если запрос:

  • напрямую JOIN-ится на Plan_Year_Enter,
  • и считает студентов,

то один план возвращается несколько раз — по каждому PrK_Plan_Year, с разным количеством студентов.

Почему это критично для расписания

Расписание формируется:

  • на учебный план,
  • для реальных групп и студентов.

Plan_Year_Enter — вспомогательная таблица, и её нельзя использовать как уникальный ключ учебного процесса.

Рекомендации

  1. Агрегировать данные по FK_Plan, а не по PrK_Plan_Year.
  2. Считать студентов через COUNT(DISTINCT Entrant).
  3. Использовать Plan_Year_Enter только как фильтр по году набора.
  4. Для новых систем не копировать эту модель без переработки.

Диагностика дублей

SELECT FK_Plan, Year_Enter, COUNT(*) AS Cnt
FROM Plan_Year_Enter
GROUP BY FK_Plan, Year_Enter
HAVING COUNT(*) > 1;

Вывод

Повторяющиеся планы с разным количеством студентов — ожидаемое следствие структуры данных Plan_Year_Enter.
Любая аналитика и логика расписания должны учитывать эту особенность.
